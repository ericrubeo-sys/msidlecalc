# Deterministic spatial extraction checkpoint

2026-10-22. Data & Tooling Engineer read the full lessons, OCR evaluation/QA, data contract and deterministic tooling plan before editing. This is feature-branch evaluation tooling, not production OCR adoption or a screenshot-to-recommendation claim. No new OCR provider, dependency or network endpoint was introduced.

## Evidence and change

The prior browser run established that repeatable text can still concatenate adjacent value/delta columns. A parser cannot safely recover the missing boundary by splitting a digit string. Engine confidence cannot resolve it. The installed pinned Tesseract.js7.0.0 [API documentation](https://github.com/naptha/tesseract.js/blob/v7.0.0/docs/api.md#worker-recognize) says only text is returned by default; blocks must be requested explicitly. Installed `src/index.d.ts` defines blocks → paragraphs → lines → words with `bbox` coordinates. Those local pinned sources were read directly, rather than inferring boxes from text spacing. Upstream capability is distinct from our extraction implementation or accuracy.

`public/domain/ocr-extraction.js` provides pure versioned proposals. `extractSpatialObservation` retains exact raw text and newline occurrences, all structured line/word observations in engine order, confidence metadata, crop-local boxes and boxes transformed back to original image pixels. Unknown and repeated rows remain distinct. Explicit normalized nonoverlapping column intervals classify only words wholly inside one interval. Boundary-spanning words stay unassigned; digits are never split or substituted. No reviewed intervals means no classified value proposal. A proposed percent sign is retained as a unit token without assigning game semantics. Every row has null confirmed value/stat ID and needs review. Punctuation and unparsed value strings carry issues; none becomes zero.

The local harness now requests `text:true, blocks:true`. Full-image and old explicitly labeled example crops remain available. A new **User-reviewed regions and columns** mode accepts up to six explicit unique panel IDs, normalized boxes, and optional ordered `labelEnd`/`valueEnd` column cuts. This supports other layouts through review rather than pretending fixed example coordinates detect panels. IDs and current/candidate attribution are supplied by the reviewer, never inferred from side or color. Regions are validated before running. The unmodified local original remains in memory.

With column cuts, each label/value/delta crop is independently recognized. This prevents the engine from joining neighboring columns in that pass, while preserving the whole-panel original observation. `assembleColumnObservations` associates rows only when vertical overlap is unique in both directions and greater than half the smaller height. Ambiguous and unmatched observations remain available, including extra or unequal lines. All original column outputs are retained even when association fails. This heuristic is a reviewed proposal, not a verified universal layout detector. Wrapped labels, tightly spaced lines and segmentation differences can prevent association. Missing or merged words remain unknown and must be corrected.

Run settings record extraction version/output formats and reviewed regions. Each panel records an explicit segmentation identity (crop, scale and column cuts) so the session owner can invalidate correction certainty when layout changes. Existing raw-text correction IDs are not replaced with inferred label identities. The session owner must retain corrections with a review warning when segmentation changes, even if repeated text happens to match.

## Verification and adoption boundary

Eight owner tests use invented text/geometry only: neighboring signed deltas; boundary-spanning concatenations; duplicate and blank observations; punctuation/lookalikes/missing values; original-coordinate transforms; detached inputs and absent blocks; malformed boxes/overlapping intervals/overflowing extents; unequal column sets and ambiguous vertical matches; terminal-whitespace proposals with untouched originals. Owner tests and harness syntax check passed. Independent QA and integration-owner browser runtime checks are separate evidence. No player raw text or stat set was added to tracked tests or this report.

Version `spatial-proposals-2` corrects a runtime finding: Tesseract line text can contain terminal newlines. Label proposals now trim terminal whitespace consistently with value/delta proposals, while original observations remain exact. The scorer is unchanged. Independent QA also found that finite enormous crop fields could produce infinite derived coordinates; extent/scaled-dimension overflow is now rejected. The harness image limits already prevent that particular malformed geometry.

The integration owner must restart the evaluation server/reload before testing changed browser code. Select the authorized example, visually review pixel crop and cuts, compare proposals against privately recorded ground truth, and report exact numerator/denominator, missing/extra/association errors and correction effort. Repeated output equality is not accuracy. Only the public example is currently permissioned; representative held-out imagery/browser variation and a reviewed application adapter remain adoption gates. This checkpoint makes no numerical OCR-accuracy claim before those runtime measurements.

Pixel/text processing remains browser-local with explicit pinned same-origin resources, no OCR fallback, no image upload endpoint and no screenshot persistence. The preexisting audit/resource gate remains in place; worker globals are still outside main-page instrumentation. More JSON shown locally is not an export or collection feature. Raw output remains active-memory only unless the integration owner deliberately records private permitted evaluation evidence outside source control.
